# 摘要与引言的通用写作大纲

## 使用范围与优先级

这是用户确认的默认写作框架，适用于不同研究方向，不限定开集识别、射频信号、联邦学习或某一种方法。先从当前材料确定研究任务、场景、机制和证据，再填入结构。

当前用户要求、事实与数学准确性、期刊要求优先于本大纲。本大纲在该用户的摘要和引言写作中优先于 section-playbook.md 与 section-blueprints.md 的通用句数和段落安排。语言、引用与协作偏好见 [user-style-profile.md](user-style-profile.md)。

段数与句数是组织起点，不是硬性配额。允许按复杂度合并或拆分，但不能省略问题与原因之间的逻辑，也不能为了凑结构虚构缺陷或矛盾。

## Abstract

默认一个自然段，约 6～7 句。摘要压缩整条论证，不展开文献综述、实现细节和理论推导。

| 位置 | 句子功能 |
|---|---|
| 第 1 句 | 直接说明研究任务及其价值 |
| 第 2 句 | 从具体应用场景引出实际困难，确有转折时可用“然而”衔接 |
| 第 3 句 | 分析困难的原因，将实际问题转化为技术要求 |
| 第 4 句 | 进一步解释关键要求、真实存在的权衡或现有方法缺少的能力 |
| 第 5～6 句 | 给出方法名称与核心设计，解释设计如何回应前面的要求 |
| 最后一句 | 陈述有实验支持的结论，说明方法的效果与适用范围 |

按句子功能理解位置。方法只需一句时，全段可为 6 句；需要两句时可为 7 句。问题简单时也可合并分析句。

逻辑顺序为 任务与价值 → 实际问题 → 原因与技术需求 → 方法 → 实验结论。

- 第一、二句先建立任务和场景，不突然抛出尚未介绍的对象。
- 第三、四句回答“为什么难”，不只重复“性能不足”。
- 存在两种要求时，解释各自需要什么，不强行写成不可兼容的矛盾。
- 方法句说明具体动作及作用，避免只列组件名称。
- 最后一句直接报告支持的结果，不默认堆叠数据集、评分函数和数字。
- 默认不放引用、公式、项目列表或贡献清单。必要缩写在首次出现时定义。

## Introduction 的总体结构

默认包含 8 个自然段，另加 3 条贡献。

- 第 1～4 段建立背景、回顾进展、提出并分析本文问题。
- 第 5～7 段位于 Motivation and Contribution 小节，依次说明研究目的、设计推理和整体框架。
- 第 7 段末尾接贡献引导句，再列 3 条贡献。
- 第 8 段单独介绍文章安排。

引言解释摘要中省略的原因，不逐句扩写或复制摘要。

与 Related Work 的分工是，引言通过少量代表性研究建立本文问题，Related Work 再展开研究思路、适用条件和方法之间的关系。两部分使用一致的问题定义和术语，避免重复整段背景或同一篇文献的相同介绍。相关工作的具体组织见 [related-work-outline.md](related-work-outline.md)。

### 第 1 段　任务背景与研究价值

约 3～4 句。

1. 开头说明研究对象、任务及其重要性。
2. 中间解释任务的基本原理或实现依据，复杂时可用两句。
3. 结尾说明这些依据支持什么能力。

从具体任务进入，不堆砌宏观背景，不提前介绍自己的方法。

### 第 2 段　现有技术与应用要求

约 4～5 句。

1. 说明现有技术已经能够做到什么。
2. 指出其成立所需的假设或条件。
3. 解释实际应用中的变化如何影响这些条件。
4. 说明影响造成的具体后果，并引出相应需求。后果和需求较复杂时拆成两句。

这里建立领域层面的研究需求，为后文聚焦本文问题铺路。不要一开始就介绍待提出的方法。

### 第 3 段　代表性研究进展

约 4～6 句。

1. 开头归纳已有工作的主要方向。
2. 中间用约 2～4 句介绍代表性研究，每项交代处理思路及其解决的问题。
3. 结尾总结已有进展和适用范围。

按问题与方法思路组织，不按年份流水排列。完整分类留给 Related Work。不要为了突出创新笼统否定所有已有方法。

### 第 4 段　本文问题及其原因

约 4～6 句，顺序为 具体场景 → 实际不足 → 原因或约束 → 技术要求。

1. 开头引入本文关注的具体条件或场景。
2. 说明已有处理方式在这里有什么不足。
3. 分析不足由什么机制、假设或现实约束造成。
4. 将困难转化为明确的技术要求。
5. 必要时解释多个要求之间的关系，以及为什么既有能力不自然保证这些要求同时成立。

问题与原因可以放在同一段。到段末读者应知道“为什么需要新的设计”，但还没有被具体模块和损失函数打断。

## Motivation and Contribution

保持这一英文标题，中文工作稿的正文仍用中文。

### 第 5 段　明确研究目的

独立短段，通常 1～2 句。

说明希望提升什么能力、针对什么困难、探索解决什么技术问题。可以用“为提升……，本文探索如何……”组织，但不要机械复用同一句式。

简述目的即可，不重复上一段完整背景，不从理论定义或组件清单开头。

### 第 6 段　从依据推导设计

约 5～7 句，按实际机制灵活安排。

1. 从技术要求出发，给出基本解决思路。
2. 在需要支撑设计的位置引入理论、观察或已有研究。
3. 解释基本思路解决了哪部分问题。
4. 若确实仍有缺口，说明缺少的能力或需要处理的影响。
5. 自然引出针对性设计，说明它具体改变什么。
6. 交代关键设计怎样配合，使推理回到任务目标。

基本链条为 需求 → 依据或思路 → 能解决什么 → 尚需满足什么 → 针对性设计。

- 不要求每篇论文都先引入一种方法，再制造其副作用。只有确有这种因果关系时才采用该结构。
- 理论在能够解释设计的位置出现，随后直接说怎么做、有什么作用，不插入独立的教材式介绍。
- 在一个连续推理段内衔接，不因为理论名称或阶段名称出现就另起段。
- 不依赖“首先”“其次”“在此基础上”串联模块。
- 对已知依据准确引用，对自己的设计清楚说明，不把整个方法写成对某篇文献的复述。

### 第 7 段　框架概述与贡献引导

约 2～3 句。

1. 用“结合上述分析，本文提出……”或自然的同类表述给出方法名称与任务。
2. 概括核心思想和主要设计如何完成最终任务。这里可简述推理方式，但不重复实现细节。
3. 直接接“本文的主要贡献如下。”，不另起段。

模型冻结、参数上传、批大小等细节原则上放在方法或实验设置，不塞进这一总结段，除非它们本身构成核心创新。

### 三条贡献

默认各用 1～2 句，保持精炼，分别承担不同功能。

| 条目 | 主要功能 | 应包含的内容 |
|---|---|---|
| 第一条 | 问题与整体方案 | 解决什么实际问题，给出什么框架，带来什么能力 |
| 第二条 | 具体方法创新 | 最有辨识度的技术动作，以及它如何回应技术需求 |
| 第三条 | 实验验证 | 实验支持什么结果或机制，必要时先用一句说明推理方式 |

- 第一条保持宏观，不从损失函数或模块组合写起。
- 第二条说具体构造、约束或优化动作，不仅列模块名称，也不依赖“继承关系”等标签。
- 第三条优先给出实验结论，而不是只列做了对比、消融、敏感性分析。推理方式仅在有助于理解验证对象时加入，不强制所有论文都有评分函数。
- 避免三条都以“提出”开头，可自然选择“提出”“设计”“构建”“实验结果表明”等。
- 不重复前面的完整方法段，不引入此前未说明的新机制。
- 实验结论的强度由实际证据决定，不因示例使用 SOTA 就套用相同结论。

### 第 8 段　文章安排

在贡献列表后单独成段，通常 2 句。

1. “本文其余部分组织如下。”
2. 按实际章节顺序说明各节内容，可合并相邻方法章节。

使用 Section II 等规范引用，核对真实编号与内容，不复制示例论文的任务、实验场景或章节安排。

## 可迁移示例

以下只是展示逻辑，不能作为后续论文的固定内容。

- 在开集识别论文中，问题可来自新场景下的未知拒识，方法需要回应相关的表征与判决要求。
- 在资源受限的信号处理论文中，问题可来自计算预算与处理质量的要求，设计应解释如何利用信号结构或优化计算。
- 无论主题如何变化，都先确认真实问题与证据，不预设一定存在两种冲突需求，也不预设必须使用投影头、联邦训练或 ETF。

## 写作前后检查

写作前先为每段指定一句功能说明，再起草正文。句子顺序应让前一句为后一句提供理由。

检查是否先有场景和问题，再有原因与要求，最后才有设计。理论是否为设计服务，贡献是否分工明确，结果是否与证据对应。

若用户只要求某句话或段落的局部修改，保持其他已确认内容不变。不能借应用此大纲擅自重构全文。
